# Практична робота №7 — Комплексне тестування та аудит якості TaskFlow

**Тема:** функціональні сценарії, аудит доступності Lighthouse та базові модульні перевірки JavaScript.

## 1. Опис проєкту

TaskFlow — адаптивний демонстраційний вебзастосунок для керування завданнями. У межах практичної роботи №7 попередній проєкт доповнено перевірками бізнес-логіки, тестовим чеклістом, рекомендаціями щодо Lighthouse та окремим файлом нативних assertions.

## 2. Запуск

1. Завантажте репозиторій або розпакуйте ZIP-архів.
2. Відкрийте `index.html` у браузері або запустіть локальний сервер:
   ```bash
   python -m http.server 8000
   ```
3. Перейдіть на `http://localhost:8000`.
4. Відкрийте DevTools клавішею `F12` → вкладка **Console**.
5. Після завантаження сторінки перевірте повідомлення `TaskFlow: модульні перевірки завершено...`. Повідомлень `Assertion failed` бути не повинно.

Зовнішні бібліотеки та тестові фреймворки не використовуються.

## 4. Функціональне та граничне тестування (Test Checklist)

Наведена таблиця містить очікувану поведінку та результати, які потрібно підтвердити під час ручного прогону у браузері. Статус PASS ставиться після фактичного виконання відповідного сценарію.

| № | Назва сценарію та вхідні дані | Очікуваний результат | Фактичний результат / перевірка | Статус |
|---:|---|---|---|---|
| 1 | Позитивний: додати завдання з назвою «Підготувати звіт» | Нова картка з’являється у списку без перезавантаження | Передбачено обробником форми; перевірити у браузері | NOT RUN |
| 2 | Порожнє введення: відправити форму без назви або ввести пробіли | HTML `required` та `validateTaskTitle()` не дозволяють додати порожній запис | Валідація реалізована; перевірити повідомлення браузера | NOT RUN |
| 3 | Гранична довжина: вставити 251+ символ у пошук | Рядок не ламає картки; фільтр працює, горизонтального переповнення немає | Пошукове значення виводиться як текст; перевірити ширини 375/768/1440 px | NOT RUN |
| 4 | XSS: ввести `<img src=x onerror=alert(1)>` у пошук | Код не виконується; рядок обробляється як звичайний текст | Результати створюються через `textContent`; перевірити відсутність alert | NOT RUN |
| 5 | Клавіатура: пройти Tab, активувати кнопки Enter/Space | Фокус видимий, усі дії доступні з клавіатури | Нативні button/input/select та `:focus-visible`; перевірити вручну | NOT RUN |
| 6 | Стійкість: швидко натиснути «Оновити» кілька разів | Не виникає помилок; попередній таймер скасовується, показується актуальний стан | `clearTimeout()` скасовує попередній таймер; перевірити у браузері | NOT RUN |
| 7 | Негативний пошук: ввести неіснуючий запит | Відображається Empty State; скидання повертає список | Реалізовано в `updateContentOrEmpty()` | NOT RUN |
| 8 | Видалити всі завдання | Відображається Empty State; можна відновити початковий список | Реалізовано обробниками видалення та кнопкою відновлення | NOT RUN |

**Примітка:** `NOT RUN` означає, що сценарій ще потрібно особисто виконати у браузері. Не позначайте ручні перевірки як пройдені без фактичного запуску. Після перевірки замініть статус на `PASS` або `FAIL` та за потреби опишіть знайдений дефект.

## 5. Перевірка адаптивності

Виконати у Chrome DevTools:

1. Натиснути `F12`.
2. Увімкнути Device Toolbar (`Ctrl + Shift + M`).
3. Перевірити три ширини:
   - **375 px** — мобільний екран;
   - **768 px** — планшет;
   - **1440 px** — настільний екран.
4. На кожній ширині перевірити Content, Loading, Empty та Error, а також UI-Kit Showcase.
5. Переконатися, що немає горизонтальної прокрутки, обрізаного тексту або накладання компонентів.

| Ширина | Що перевірити | Фактичний результат | Статус |
|---:|---|---|---|
| 375 px | Одна колонка карток, кнопки переносяться, немає горизонтального скролу | Заповнити після перевірки | NOT RUN |
| 768 px | Дві колонки карток, панелі не накладаються | Заповнити після перевірки | NOT RUN |

## 6. Lighthouse — аудит якості

### Як запустити
1. Відкрийте сторінку через локальний сервер або опублікований GitHub Pages URL.
2. Відкрийте DevTools → **Lighthouse**.
3. Оберіть режим **Navigation**, пристрій Desktop або Mobile.
4. Позначте категорії **Accessibility**, **Best Practices**, **SEO**.
5. Натисніть **Analyze page load**.
6. Збережіть отримані показники та зауваження.

### Результати аудиту

| Категорія | Бал Lighthouse (0–100) | Зауваження / виконані виправлення |
|---|---:|---|
| Accessibility | Внести фактичний бал | Семантичні кнопки, пов’язані label, aria-label для іконічних дій, видимий фокус |
| Best Practices | Внести фактичний бал | Нативний JavaScript, відсутність сторонніх бібліотек, безпечний вивід тексту |
| SEO | Внести фактичний бал | Наявні `title`, `meta description`, `lang="uk"` та viewport |

**Важливо:** оцінки Lighthouse залежать від браузера, режиму, мережі та середовища запуску. Вони не можуть бути достовірно визначені без фактичного запуску аудиту. Впишіть числа зі свого звіту Lighthouse, не використовуйте вигадані значення.

## 7. Модульні перевірки (Unit Assertions)

У `app.js` створено дві чисті функції:

- `validateTaskTitle(value)` — перевіряє тип, непорожнє значення після `trim()` та максимальну довжину 80 символів.
- `isValidScreenState(state)` — перевіряє, чи належить назва стану до списку `loading`, `content`, `empty`, `error`.

Функції не звертаються до DOM і не змінюють дані. Вони експонуються через `window.TaskFlowUtils` як незмінний об’єкт.

У `tests.js` функція `runUnitTests()` перевіряє:
1. Коректну назву завдання.
2. Порожній рядок.
3. Рядок лише з пробілів.
4. Рядок довший за 80 символів.
5. Значення неправильного типу.
6. Допустимий і недопустимий стан екрана.

Тести запускаються після завантаження DOM. Вони лише читають результати чистих функцій, не змінюють DOM, тему або користувацькі дані. Успішні `console.assert()` не виводять помилок; при невдалій умові браузер покаже `Assertion failed`.

## 8. Перевірка захисту від XSS

Динамічний вміст карток формується через `document.createElement()` та запис властивостей `textContent`. Значення пошуку лише порівнюється з текстовими полями, а не вставляється у HTML. Тому введений HTML-подібний рядок не інтерпретується браузером як розмітка чи JavaScript.

У коді не слід використовувати `innerHTML` для виведення даних, які ввів користувач.

## 9. Контрольні запитання та відповіді

### 1. У чому різниця між позитивним та граничним (негативним) тестуванням?
Позитивне тестування перевіряє штатні сценарії з коректними даними: наприклад, введення правильної назви та успішне додавання завдання. Негативне й граничне тестування перевіряє реакцію системи на некоректні або незвичні дані: порожній рядок, пробіли, надмірну довжину, спеціальні символи. Мета — переконатися, що застосунок не ламається та правильно повідомляє про помилки.

### 2. Як `textContent` замість `innerHTML` захищає від XSS?
`textContent` вставляє значення як звичайний текст і не аналізує його як HTML. Тому рядок на кшталт `<img src=x onerror=alert(1)>` відображається як текст, а не створює HTML-елемент із обробником події. `innerHTML`, навпаки, інтерпретує рядок як розмітку, що може створити XSS-ризик.

### 3. Що оцінює Lighthouse у категоріях Accessibility та Best Practices?
Accessibility перевіряє доступність інтерфейсу: підписи елементів керування, доступні назви, контрастність, семантичну структуру та інші рекомендації для користувачів із різними потребами. Best Practices перевіряє дотримання сучасних практик веброзробки, зокрема безпечне використання API, коректність ресурсів і відсутність типових проблем браузерної реалізації. Конкретний набір перевірок може змінюватися залежно від версії Lighthouse.

### 4. Як працює `console.assert(condition, message)`?
Метод перевіряє логічну умову. Якщо `condition` дорівнює `true`, повідомлення не виводиться. Якщо умова хибна, у консолі з’являється повідомлення `Assertion failed` із переданим текстом. Метод не зупиняє виконання програми, тому його зручно використовувати для простих перевірок.

### 5. Чому бізнес-логіку для тестів потрібно оформлювати як чисту функцію?
Чиста функція залежить лише від переданих аргументів і повертає результат без побічних ефектів. Вона не читає DOM, не змінює глобальний стан і не залежить від порядку взаємодії користувача зі сторінкою. Завдяки цьому її легко перевіряти різними наборами вхідних даних, а результати тестів є передбачуваними та відтворюваними.

## 10. Висновок

Під час виконання практичної роботи проєкт TaskFlow було доповнено базовими засобами забезпечення якості. Сформовано функціональний чекліст із позитивними, негативними та граничними сценаріями; підготовлено інструкцію для перевірки адаптивності на ширинах 375, 768 і 1440 px та проведення аудиту Lighthouse. Реалізовано чисті функції валідації й перевірки станів, а також окремий файл `tests.js` із нативними `console.assert()`. Динамічні користувацькі дані виводяться через `textContent`, що знижує ризик XSS під час відображення тексту. Таким чином, проєкт отримав основу для повторюваного ручного та автоматизованого тестування без сторонніх залежностей.
